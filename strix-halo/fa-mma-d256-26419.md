# FA MMA_F16 at D=256 on gfx1151 — evaluating upstream PR #26419

## Status (2026-08-29 — benched, all four arms; **not adopting**)

Upstream [PR #26419](https://github.com/ggml-org/llama.cpp/pull/26419) (srgtuszy, open since
2026-08-01) widens the FlashAttention dispatcher so AMD WMMA parts take the **MMA_F16** kernel at
head dim 256 instead of the **TILE** kernel. gfx1151 is inside the widened gate. If it merges as
written, **this fork's `fattn-tile.cuh` patch stops firing at prefill** — the kernel it tunes is no
longer the kernel that runs.

Every validation report on the PR was RDNA4 (gfx1201) and nobody had benched it on RDNA3.5. We now
have: **it costs 4.7% of prefill at d=16k on stock upstream and 11.6% on our tree.** See
[Outcome](#outcome). The plan and predictions below are kept as written, including the one that was
wrong.

## Why this is not a retry of Finding #7

[Finding #7](jg-cuda-fa-rdna3-4.md) measured MMA at D=256 on this chip at **-22.5%** (pp512@d=16k
851 -> 660 t/s) and [fa-rdna3-opsel-pair.md](fa-rdna3-opsel-pair.md) localized the cost to the f32
`T_C_VKQ` accumulator: 8 VGPRs/lane against RDNA4/CDNA's 4, pinning VGPR/wave at 256 and occupancy at
6 waves/SIMD. The conclusion recorded then was that the ceiling is structural and the fix has to come
from upstream.

**That fix has already landed and we did not notice.** In current
[fattn-mma-f16.cuh:1045-1053](../ggml/src/ggml-cuda/fattn-mma-f16.cuh#L1045-L1053) the generic-`DV`
RDNA3 accumulator is:

```cpp
using T_C_VKQ = tile<16, 16, half2, DATA_LAYOUT_I_MAJOR>;          // RDNA3
using T_C_VKQ = tile<16, 16, half2, DATA_LAYOUT_I_MAJOR_SCRAMBLED>; // RDNA4
```

Same element type, same shape — the two differ only in data layout. The f32 accumulator survives
only in the `DV=80` and `DV=112` specializations, neither of which is our shape. This was already
true at our previous base `221f0f635`, so it predates this sync; `fa-rdna3-opsel-pair.md` has been
stale on the point for some months. **The register-pressure argument for why MMA loses at D=256 on
RDNA3 no longer holds.** Whether it now wins is an open question, which is the point of benching.

What still differs between RDNA3 and RDNA4 on this path: the `MIRRORED` data layouts on the RDNA3
A/B tiles, and the RDNA3 mask-layout special case at
[fattn-mma-f16.cuh:764-782](../ggml/src/ggml-cuda/fattn-mma-f16.cuh#L764-L782). Those are why the
RDNA4 numbers on the PR do not transfer.

## What the PR changes

Three commits, `+67/-6`, touching `fattn-mma-f16.cuh`, `fattn.cu`, `tests/test-backend-ops.cpp`:

1. `48a108d31` — for `DKQ > 128` on AMD WMMA, load K/V straight from VRAM instead of staging through
   LDS. The PR author reports MMA is *slower* than TILE at D=256 without this.
2. `d273e0b48` — the dispatcher widening plus an `nbatch_combine` 64 -> 128 precision fix at
   `DKQ=256` (multi-pass FP16 accumulation error in `test-backend-ops`).
3. `d76c00469` — fixes a `tile_mask` write-after-read race the LDS bypass introduced, since
   `tile_mask` still lives in LDS when K/V no longer do.

The dispatcher hunk in [fattn.cu:515](../ggml/src/ggml-cuda/fattn.cu#L515):

```cpp
-    if ((amd_wmma_available(cc) && gqa_opt_applies && Q->ne[0] <= 128) && ... && Q->ne[1] * gqa_ratio_eff > 8) {
-        return BEST_FATTN_KERNEL_MMA_F16;
+    if (amd_wmma_available(cc) && gqa_opt_applies && Q->ne[0] != 40 && Q->ne[0] != 72) {
+        if (Q->ne[0] <= 128 && Q->ne[1] * gqa_ratio_eff > 8)  { return BEST_FATTN_KERNEL_MMA_F16; }
+        if (Q->ne[0] <= 256 && Q->ne[1] * gqa_ratio_eff > 64) { return BEST_FATTN_KERNEL_MMA_F16; }
     }
```

This mirrors the existing CDNA/MFMA structure at
[fattn.cu:501-511](../ggml/src/ggml-cuda/fattn.cu#L501-L511) exactly, which is a point in its favour
for merge odds.

## Why it fires on our workload

`amd_wmma_available(cc)` is `RDNA4 || RDNA3` ([common.cuh:341](../ggml/src/ggml-cuda/common.cuh#L341))
and `GGML_CUDA_CC_IS_RDNA3` covers RDNA3.5 ([common.cuh:89](../ggml/src/ggml-cuda/common.cuh#L89)),
so gfx1151 is in the gate. Qwen 3.6 35B-A3B is head dim 256, so `ncols2_max = 8` and `gqa_ratio_eff`
saturates at 8.

| phase | `Q->ne[1]` | `Q->ne[1] * gqa_ratio_eff` | `> 64`? | kernel |
|---|---:|---:|:--:|---|
| prefill, `-ub 2048` | 2048 | 16384 | yes | **MMA_F16** (changes) |
| decode | 1 | 8 | no | TILE (unchanged) |

So the switch is **prefill-only**. Our `fattn-tile.cuh` override keeps working at decode, where it
was never doing much — the 2026-07-18 profile puts FA at 0.7-8.5% of decode time. It stops applying
at prefill, where FA is 32% of the budget at d=16k and where the patch was earning its keep.

This also means the patch does not conflict with the PR in the textual sense. It goes dead by
dispatch, silently, with no merge conflict to warn us. Exactly the failure mode
[findings.md § how #6 got away from us](findings.md#how-6-got-away-from-us) describes.

## Arms

All four on ROCm 7.14.0, canonical bench, same host, same session. Arms B and D are the ones that
answer the question; A and C are the controls that make the answer interpretable.

| arm | tree | what it isolates |
|---|---|---|
| **A** | upstream `c841aeeb8`, clean | upstream-only baseline at the new tip |
| **B** | A + #26419 | the PR's effect on stock upstream, no fork patches |
| **C** | fork `master` (= A + our three patches) | **mandatory post-rebase re-bench**, per [upstream.md](upstream.md#re-bench-checklist) |
| **D** | C + #26419 | does MMA beat our tuned TILE on the production tree? |

`B - A` is the PR's standalone value on gfx1151 — the number the PR thread is missing.
`D - C` is what the PR costs or earns *us*, given we already tuned the kernel it bypasses.
`C - A` is the long-owed fork-patch attribution ([backlog.md](backlog.md) item 2), which falls out of
this matrix for free since both builds are needed anyway.

## Predictions, recorded before the bench

1. **Decode is flat in every arm.** The dispatch arithmetic above says decode never leaves TILE. If
   tg128 moves more than the +/-2% noise floor, something in the analysis is wrong and the prefill
   numbers should not be trusted either. This is the control.
2. **`B > A` at depth.** The PR's mechanism is real and RDNA3 no longer carries the f32 accumulator
   penalty. Direction predicted, magnitude not — RDNA4 saw +13.6% at d=16k, and gfx1151 has roughly a
   quarter of the bandwidth and a different tile layout, so it should not be assumed to transfer.
3. **`D - C` is smaller than `B - A`.** Arm C already tuned TILE at this shape (`nbatch_K` 128 -> 64),
   so part of the PR's headroom on stock upstream is headroom we have already taken. `D < C` at any
   depth is a live possibility and is the outcome that matters most to report upstream.
4. **`C > A` at d=0.** Finding #9 claimed +27% prefill and it has never been verified by
   port-off. If this comes back flat, the MMQ retune's value is in question and backlog item 2 is
   answered the hard way.

## Outcome

**All four arms benched 2026-08-29.** Same host, same day, canonical bench with `-lm none`. Arms C
and D were run twice; the tables below use the mean of two runs for those.

**PR #26419 is a regression on gfx1151, and it gets worse with depth** - the opposite sign *and* the
opposite depth-trend from every RDNA4 report on the PR thread.

**Prediction 1 held completely.** Decode is identical across all four arms to within 0.2% at every
depth. The dispatch analysis was right: at `ne[1]=1` the new `> 64` test fails and TILE is retained,
so the PR cannot and does not touch decode. Arm D run 1 showed a -1% dip with an anomalous ±1.58
error bar at d=2048; run 2 came back 50.79 ± 0.27 and it did not reproduce. It was noise.

### This closes the port-off attribution (backlog item 2)

`C - A` is **+27.6% to +29.2% prefill**, uniform across depth, with decode flat to within 0.2%:

| depth | A upstream | C fork | **C - A** |
| ------: | ------: | ------: | ------: |
|       0 | 1077.79 | 1377.80 | **+27.8%** |
|   2,048 |  974.19 | 1259.02 | **+29.2%** |
|   8,192 |  864.05 | 1109.48 | **+28.4%** |
|  16,384 |  746.32 |  952.12 | **+27.6%** |

**Correction, same day:** a third build isolated `mmq-config-rdna3-5.cuh` alone and it is worth only
**+2.1% to +4.2%** - 8-15% of this gain. The `C - A` figures above are the *bundle* of all three
patches, not the MMQ table, and this doc briefly said otherwise. See
[qwen3.6-baseline.md](qwen3.6-baseline.md#2026-08-29--post-rebase-re-bench-build-df16ecb).

Both arms share the identical upstream base `c841aeeb8`; the only difference is our three patched
files. Prediction 4 is confirmed and more strongly than it was written - the gain holds at every
depth, not just d=0. The flat decode tie is what makes it trustworthy: no patch this fork carries can
move decode, so a clean tg control is what a single-variable A/B is supposed to look like. Every
prior statement of this gain was inferred from before/after builds across moving upstream; this is
the first measurement against a matched control.

### Reading the #26419 result

**d=16,384 is the trustworthy row and the decisive one.** Arm D reproduced at 841.91 and 841.37
across independent runs (0.06% apart) with the tightest error bars in the matrix, against arm C's
equally reproducible 952.16 / 952.07. The shallower rows sit inside this build generation's inflated
variance and should not be quoted.

The PR loses on **both** bases, and loses about 2.5x more with our patches in:

- **On stock upstream (`B - A`): -4.7% at d=16k.** MMA at D=256 is simply slower than upstream's own
  TILE kernel on this chip.
- **On our tree (`D - C`): -11.6% at d=16k.** Larger because our TILE config is faster than stock
  TILE, so switching away from it forfeits more. This is prediction 3's reasoning - part of the PR's
  headroom on stock upstream is headroom we already took - but with the sign inverted from what was
  written down.

**Prediction 2 was wrong.** It said `B > A` at depth, on the grounds that the f32 accumulator that
sank Finding #7 had been replaced with half2. The accumulator fix is real and is documented above,
but it was not sufficient: MMA at D=256 still loses on RDNA3.5. Whatever the remaining cost is, it is
not the accumulator - the `MIRRORED` data layouts and the RDNA3 mask special case at
[fattn-mma-f16.cuh:764-782](../ggml/src/ggml-cuda/fattn-mma-f16.cuh#L764-L782) are the untested
candidates.

**The depth-trend is the most interesting part for upstream.** On RDNA4 the PR's gain *grows* with
depth (+13.6% at 16k and +21.8% at 127k from the author; +62% at 100k from a third party). On gfx1151
it goes the other way: roughly neutral at 2k-8k, then falls off a cliff at 16k. Two architectures on
the same code path with opposite depth-scaling is a real signal, not a tuning nit.

### Consequences for this fork

- **Our `fattn-tile.cuh` patch is vindicated, not superseded.** The premise of this experiment was
  that #26419 would silently retire it. Instead it is worth defending: on our tree, keeping TILE is
  worth +11.6% at d=16k over taking the PR's MMA path.
- **[backlog.md](backlog.md) item 1 (FA TILE D=256 tuning) survives and is better motivated.** TILE is
  confirmed the right kernel for this shape on this chip, so sweeping `nthreads`, `occupancy` and
  `nbatch_fa` tunes the kernel we will actually keep running.
- **Nothing to change on master.** No commit results from this experiment; the outcome is a decision
  not to adopt, plus numbers to report.
- **These numbers belong on PR #26419.** It has no RDNA3.5 data point and the thread has asked for
  one. The useful framing is the gate, not a veto: the RDNA4 gains are real and well-evidenced, and
  narrowing the `<= 256` arm to RDNA4 keeps them while sparing RDNA3.5.

### Caveat carried from arm C

This matrix sits on a build generation whose prefill variance is 3-30x the historical noise floor and
whose absolute prefill is 2.5-5.3% below `b73cfa4`, for reasons traced to upstream rather than to us
(see [qwen3.6-baseline.md](qwen3.6-baseline.md#2026-08-29--post-rebase-re-bench-build-df16ecb)).
Because all four arms share that condition, the **within-matrix** comparisons above are sound, and
the d=16k rows in particular reproduce tightly. What cannot be done is comparing these absolute
numbers to the `b73cfa4` era. The `-funsafe-math-optimizations` restore build remains outstanding.
